# Ollama Agent — LLM Tool-Use Evaluation Harness

Evaluates how well LLMs (via Ollama) generate, compile, and test Java programs through a reactive agent loop with function-calling tools.

## Architecture (Single-Session)

```
toto.sh ──iterates──▶ complete.sh ──POST──▶ Ollama /api/chat
                        │                        │
                        ▼                        ▼
                   parser.py ◀──── JSON response (tool_calls + content)
                        │
                        ▼
                   Tool dispatch (write_file / javac / java)
                        │
                        ▼
                   Result fed back as {"role": "tool"} message
                        │
                        ▼
                   Repeat until no tool calls or MAX_STEPS (10)
                        │
                        ▼
                   Automated test harness (SHA-256 validation)
```

## Ralph Loop Architecture (Multi-Turn)

The Ralph Loop wraps the single-session architecture into a persistent,
long-running agent. State is stored on the filesystem (not in the LLM's context
window), preventing context rot over dozens or hundreds of turns.

### Spec-Driven Architecture (v2)

The markdown spec is replaced by a structured YAML spec (`spec.yaml`) as the
single source of truth. Task generation, verification, and progress tracking
are extracted into Python modules, keeping `ralph.sh` as a thin orchestrator.

```
spec.yaml ──→ spec_parser.py ──→ tasks.json
                                        │
                ralph.sh (thin loop) ────┤
                    │                    │
                    ├─→ complete.sh      │
                    │       └─→ parser.py│
                    │                    │
                    └─→ task_runner.py ◄─┘
                         (verify, progress, git)
```

### Key Characteristics

**A. Fresh Context Every Turn**  
Every loop turn starts a completely fresh, unpolluted context window. Memory
is re-established by reading physical files on disk at the start of each session.

**B. Layered Abstraction (Manager vs Worker)**  
`ralph.sh` (Manager) tracks tasks, verifies outputs, and commits state.
`complete.sh` (Worker) handles single-session LLM interaction via Ollama.

**C. Single-Task Focus**  
Each turn selects exactly one discrete task from a machine-readable ledger.
The LLM never attempts multiple requirements in one session.

**D. Self-Healing via Version Control**  
Every successful turn produces a Git checkpoint. Non-compiling or corrupt
output triggers `git reset --hard` to the last known good state.

### Flow

```
ralph.sh (Manager)
  │
  ├─ 1. Initialize sandbox (copy spec.yaml, prompt.hashprime.info, generate tasks.json)
  ├─ 2. Pick highest-priority "failing" task
  ├─ 3. Run profile_model.sh if needed (uses spec_parser.py metadata)
  ├─ 4. Inject task context into prompt.hashprime.info
  ├─ 5. Spawn complete.sh (Worker) with fresh context
  │
  │   complete.sh (Worker)
  │     ├─ Send augmented prompt → Ollama API
  │     ├─ Execute tool calls (write_file / javac / java)
  │     ├─ Capture model reasoning → .last_reasoning.txt
  │     └─ Run test harness (reads regression_tests from tasks.json)
  │
  ├─ 6. task_runner.py verifies:
  │     a. Regression gate — re-run tests for all passing tasks
  │     b. Task-specific verification (compile + run)
  ├─ 7. On pass: update tasks.json, append reasoning to CHANGELOG.md, git commit
  │   On fail: git reset --hard
  └─ 8. Repeat until all tasks passing or MAX_TURNS
```

## Scripts

### `toto.sh` — Batch Runner

Iterates every model in `ollama list` (excluding `embed` and `ocr` models), stops any running models between runs with `kill_ollama_models()`, and invokes `complete.sh <model>` for each one. Output is tee'd to `logs/<model>_<timestamp>.txt`.

```
./toto.sh
```

Deletes `logs/` and `configs/` at startup (configs are regenerated by `profile_model.sh` on demand).

---

### `ralph.sh` — Long-Running Agent Harness (Manager)

Wraps `complete.sh` into a persistent multi-turn agent with filesystem-based
memory and per-model branches. Uses `spec_parser.py`, `task_runner.py`, and
a structured `spec.yaml` for spec-driven task generation.

**Phase 1 — Initializer** (one-time):
1. Creates `sandbox/` with a separate Git repository (never touches project `.git/`)
2. Symlinks `complete.sh`, `parser.py`, `profile_model.sh`, `spec_parser.py`, `task_runner.py`, `prompts/`, `.configs/` into the sandbox
3. Copies `spec.yaml` and `prompt.hashprime.info` into the sandbox
4. Runs `spec_parser.py` to generate `tasks.json`
5. Creates `init.sh`, `CHANGELOG.md`, `progress.txt`
6. Commits initial state to `main`

**Phase 2 — Worker Loop** (iterative):
1. Checks `task_runner.check_all_completed()` for early exit
2. Reads `tasks.json` → picks highest-priority `"failing"` task
3. Checks for parser profile; runs `profile_model.sh` if needed (uses `spec_parser.py metadata`)
4. Injects task context + progress into `prompt.hashprime.info`
5. Invokes `complete.sh` in a fresh session
6. Pipes task JSON to `task_runner.py verify` for compilation + verification + git commit/rollback
7. Repeats until all tasks passing or MAX_TURNS

```
./ralph.sh qwen2.5-coder:7b 10
```

Each model gets its own branch from the same sandbox Git. Passing tasks are
committed to the model's branch; failures roll back leaving other models
unaffected.

---

### `spec_parser.py` — Spec-Driven Task Generator

Reads `spec.yaml` and generates `tasks.json`. All task metadata (IDs,
descriptions, verification commands, expected outputs) is derived from
the structured YAML spec — no hardcoded values. Also provides spec
metadata (filename, class name, spec file path) to other scripts.

```
python3 spec_parser.py spec.yaml
python3 spec_parser.py metadata  # Returns JSON: {spec_file, filename, class_name}
```

---

### `task_runner.py` — Verification, Regression Gate, Progress, Git

Handles compilation, task verification, **regression testing**, progress
tracking, and git operations. Called by `ralph.sh` after each worker session.

**Regression gate** (`_run_regression_tests`): Before the task-specific
verification, reads `regression_tests` from `tasks.json` (generated by
`spec_parser.py` from `spec.yaml`). For each previously-passing task, runs its
associated test inputs against `hashprime.java` with exact output matching. If
any passing task regressed, the entire verification fails immediately — the
code is never committed with a regression.

**Reasoning capture**: The model's final explanatory text is written to
`.last_reasoning.txt` by `complete.sh`, passed as `$RALPH_REASONING`, and
appended to `CHANGELOG.md` on successful passes. This preserves the model's
intent for post-hoc analysis.

| Command | Description |
|---------|-------------|
| `pick_next` | Print the next failing task as JSON |
| `verify` | Read task JSON from stdin, run regression gate, compile, verify, commit/rollback |
| `check_all` | Check if all spec tasks completed successfully |
| `mark_passed` | Mark a task as passing in tasks.json |

```
python3 task_runner.py pick_next
echo '<json>' | python3 task_runner.py verify <turn> <ts> <branch>
python3 task_runner.py check_all
```

---

### `profile_model.sh` — Model Probe

Probes a single model to detect which parser stage it uses. Called automatically by `complete.sh` when no parser profile exists.

**Flow:**
1. Calls `spec_parser.py metadata` to get spec file path, expected filename, and class name from `spec.yaml`
2. Reads the spec file, extracts expected filename from the `File:` line
3. Sends a diagnostic request to Ollama with the spec prompt + tool schemas
4. Runs `parser.py --probe` on the response — returns the stage number that first matches
5. Saves the detected stage to `.configs/<sanitized_model>.config.json` (e.g. `{"stage": 6}`)
6. Saves the raw Ollama response to `.configs/<sanitized_model>.raw.json`
7. Creates a thin parser wrapper `.configs/<sanitized_model>.sh`:
   ```bash
   exec python3 "$(dirname "$0")/../parser.py" --model "$(basename "$0" .sh)"
   ```
   This wrapper passes `--model <name>` so `parser.py` reads the config file and only checks the detected stage.

Retries up to 3 times. If no format is detected, the config file is deleted and `complete.sh` will fall back to the full 8-stage cascade.

```
./profile_model.sh qwen2.5-coder:7b
```

### `complete.sh` — Main Agent Loop

The core evaluation harness. Accepts a model name as its argument.

**Setup:**
1. Cleans workspace: `rm -f *.class *.java`
2. Reads `prompt.hashprime.info`, extracts expected filename via regex on the `File:` line (e.g. `hashprime.java`), derives class token (`hashprime`)
3. Builds the system prompt with the expected filename baked in
4. Dynamically generates the Ollama tool schema with `jq`, injecting the filename and class token into `description`, `examples`, and `pattern` fields
5. Selects a parser:
   - `.configs/<model>.sh` — profiled thin wrapper (fast, stage-restricted)
   - `.configs/<model>.py` — custom Python parser
   - Otherwise runs `bash ./profile_model.sh "$MODEL"` to create a profile, then uses the new `.sh`

**Reactive Loop** (max 10 steps):
1. POST to Ollama `/api/chat` with conversation messages + tool schemas
2. Parse the response through the selected parser
3. If zero tool calls on the first turn, retry once
4. If zero tool calls on later turns, check for ```sh blocks as a shell-command fallback
5. Dispatch each tool call:

| Tool | Action | Validation |
|------|--------|-----------|
| `write_file` | Writes source to disk | Rejects null/empty filename; shows content preview |
| `javac` | Compiles with `javac` | Rejects null/empty filename; captures compilation errors |
| `java` | Runs compiled class | Rejects null `class_name`; detects `ClassNotFoundException` with hints |

6. Append tool result as `{"role": "tool", "content": ...}` to the message history
7. Repeat until agent signals completion or max steps reached

**Auto-inject:** If the model omits a required parameter (null/empty filename
in `write_file` or `javac`, null class_name in `java`), the harness silently
injects the correct value from the spec (`hashprime.java` / `hashprime`).
The file is written or the command is executed as if the model had provided
the correct parameter. An `[AUTO-FIX]` message is printed to the log so the
pattern is visible during debugging. Step count still increments (the model
made a tool call), but the call is honored and no step is wasted on a
rejected error message.

**Post-Loop Harness:**
If `hashprime.java` exists:
1. Capture model reasoning from last response → `.last_reasoning.txt`
2. Compile with `javac hashprime.java`
3. Read `regression_tests` from `tasks.json` — runs each fast test input
   against `hashprime.java` with exact SHA-256 output matching
4. Reports per-test pass/fail with model name in header:
   `AUTOMATED HARNESS VALIDATION — <model>`

Tests are derived from `spec.yaml` → `tasks.json` by `spec_parser.py`:

| Test Input | Validates | Source |
|------------|-----------|--------|
| `java hashprime -5` | Empty-stream (N<2) | `regression_tests` in `tasks.json` |
| `java hashprime 0` | Empty-stream (N<2) | `regression_tests` in `tasks.json` |
| `java hashprime 1` | Empty-stream (N<2) | `regression_tests` in `tasks.json` |
| `java hashprime 11` | Small-N hash | `regression_tests` in `tasks.json` |
| `java hashprime 12` | Small-N hash (13 is prime) | `regression_tests` in `tasks.json` |
| `java hashprime 1000` | Medium-N hash | `regression_tests` in `tasks.json` |

The harness exit code is non-zero if any test fails. This is also used
by `ralph.sh` / `task_runner.py` as the regression gate between turns.

Prints wall-clock time, total tokens, and tokens/sec.

```
./complete.sh qwen2.5-coder:7b
```

### `parser.py` — Cascading Parser

Normalizes model output into a uniform tool-call format. Reads Ollama API response JSON from stdin; writes a JSON array of `{"name": "...", "arguments": {...}}` to stdout.

**8-Stage Cascade:**

| Stage | Name | What It Matches |
|-------|------|----------------|
| 1 | Native tool_calls | Ollama's `message.tool_calls[]` array (pass-through) |
| 2 | Think-tag cleanup | Strips `<think>...</think>` reasoning blocks, re-checks |
| 3 | Markdown JSON blocks | ````json {...} ```` fenced code blocks |
| 4 | Raw JSON stream | Any `{...}` in content that decodes with a `name` field |
| 5 | XML tags | `<write_file filename="..." content="..."/>` etc. |
| 6 | Markdown Java blocks | ````java ... ```` — last match wins |
| 7 | Unfenced Java | Bare `public class ...` with no backticks |
| 8 | Shell commands | ````sh` / ````bash` blocks — extracts `javac` and `java` lines |

Each stage is tried in order; the first stage to produce results wins.

**Key helper — `_extract_tool_info(obj)`:** Normalizes many key-name conventions (`name`/`tool`/`function`, `arguments`/`params`/`args`).

**Profiling mode (`--probe`):** Runs the same cascade but returns only the matching stage number. Used by `profile_model.sh`.

**Stage-restricted mode (`--model <name>`):** Reads `.configs/<name>.config.json` and skips all stages except the detected one. This speeds up parsing for profiled models.

```
echo '<ollama-json>' | python3 parser.py
echo '<ollama-json>' | python3 parser.py --probe
echo '<ollama-json>' | python3 parser.py --model qwen2.5-coder_7b
```

## `.configs/` Directory

Stores per-model parser profiles, created by `profile_model.sh`. Three files per model:

| File | Contents |
|------|----------|
| `<sanitized_model>.config.json` | `{"stage": 6}` — detected parser stage number |
| `<sanitized_model>.raw.json` | Full Ollama response from the probe |
| `<sanitized_model>.sh` | Thin bash wrapper: `exec parser.py --model <name>` |

The model name is sanitized by replacing `/` and `:` with `_` (e.g. `qwen2.5-coder:7b` → `qwen2.5-coder_7b`).

### How `complete.sh` selects a parser

```
if .configs/<model>.sh exists         → use it (profiled, stage-restricted)
elif .configs/<model>.py exists       → use it (custom parser)
else                                  → run profile_model.sh, then use the new .sh
```

This ensures models are only probed once; subsequent runs reuse the cached profile.

## Tool Schema

Three tools are registered with Ollama. The schema is built dynamically from the spec file — if the spec says `File: MyApp.java`, all descriptions and examples use `MyApp.java` / `MyApp` automatically.

| Tool | Purpose | Key Parameters |
|------|---------|---------------|
| `write_file` | Creates/overwrites Java source | `filename` (`.java`, pattern-constrained), `content` |
| `javac` | Compiles existing `.java` file | `filename` |
| `java` | Runs compiled class | `class_name`, `args[]` |

Parameters include `pattern`, `minLength`, and `examples` to guide model output.

## Prompt Files

All prompts sent to the LLM are stored as editable text files under `prompts/`.
This makes every prompt visible and editable without touching source code.

### `prompts/system.txt` — System Prompt

Sent as the `system` role message in every Ollama chat request. Provides the
LLM with the tool-use action sequence (write_file → javac → java) and
identifies the expected filename and class token.

| Placeholder | Substituted With | Source Script |
|-------------|-----------------|---------------|
| `{{FILENAME}}` | Target Java filename (e.g. `hashprime.java`) | `complete.sh` (line 72), `profile_model.sh` (uses `spec_parser.py metadata`) |
| `{{CLASS_TOKEN}}` | Class name derived from filename (e.g. `hashprime`) | `complete.sh`, `profile_model.sh` |

Default content:
```
You are an automated software engineer. ALWAYS follow this strict action sequence:
1) write_file (filename={{FILENAME}})
2) javac {{FILENAME}}
3) java {{CLASS_TOKEN}} <N>
Never attempt to run 'java' before 'javac' succeeds. Test N=11 and N=1000, then stop.
```

### `prompts/task_context.txt` — Session Goal Header

Prepended to `prompt.hashprime.info` by `ralph.sh` before each turn. Tells the
LLM which single task to focus on, what progress has been made, how the result
will be verified, and which inputs will be regression-tested between turns.

| Placeholder | Substituted With | Source Script |
|-------------|-----------------|---------------|
| `{{FILENAME}}` | Target Java filename (e.g. `hashprime.java`) | `ralph.sh` reads from `tasks.json.filename` |
| `{{TASK_ID}}` | Current task identifier (e.g. `input_validation`) | `ralph.sh` (`generate_task_prompt()`) |
| `{{TASK_DESC}}` | Human-readable task description | `ralph.sh` |
| `{{PASSING_TASKS}}` | Comma-separated list of passing task IDs | `ralph.sh` |
| `{{VERIFY_CMD}}` | Shell command used to verify the task | `ralph.sh` |
| `{{EXPECTED_OUTPUT_BLOCK}}` | Replaced with `Expected output:` + value, or removed if empty | `ralph.sh` (python3) |
| `{{REGRESSION_INPUTS}}` | List of test inputs for regression gate (`N=-5, N=0, N=1, N=11, N=12, N=1000`) | `ralph.sh` reads from `tasks.json.regression_tests` |

Only test inputs are listed — **expected hashes are omitted** to prevent the
model from hardcoding regression-test answers.

Default content:
```
=== PROJECT FILE ===
Write your implementation to: {{FILENAME}}

=== CURRENT SESSION GOAL ===

Focus exclusively on this single task: {{TASK_ID}}
Description: {{TASK_DESC}}

=== PROGRESS SO FAR ===
Passing tasks: {{PASSING_TASKS}}


=== VERIFICATION ===
After implementing, your code WILL be verified with:
  {{VERIFY_CMD}}
{{EXPECTED_OUTPUT_BLOCK}}

After verification, your code WILL be regression-tested on these inputs:
{{REGRESSION_INPUTS}}

Do NOT hardcode answers. Implement the algorithm correctly for ALL inputs.
Your code must pass both the task verification and the regression tests.
```

## OKF Knowledge Bundle

The agent includes an [Open Knowledge Format (OKF) v0.2](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md) knowledge bundle — a "second brain" that accumulates skills, failure patterns, and model knowledge over time. The bundle is human-readable (markdown), agent-parseable (YAML frontmachine), and version-controlled (git).

### Bundle Structure

```
sandbox/knowledge/
├── index.md                    # Root index with OKF v0.2 frontmatter
├── project.md                  # type: Project — spec.yaml as knowledge
├── log.md                      # Chronological update history
├── computations/               # type: Attested Computation — one per task
│   ├── index.md
│   ├── input_validation.md
│   ├── empty_stream.md
│   └── ...
├── models/                     # type: Model — per-model evaluation results
│   ├── index.md
│   └── qwen2.5-coder_7b.md
├── skills/                     # type: Skill — learned techniques
│   ├── index.md
│   ├── index.json              # Machine-searchable index
│   ├── think-tag-stripping.md
│   ├── regression-gate.md
│   └── ...
├── failure-modes/              # type: Failure Mode — known problems + fixes
│   ├── index.md
│   ├── index.json
│   ├── compile-before-write.md
│   └── endless-retry-loop.md
├── model-profiles/             # type: Model Profile — per-model characteristics
│   ├── index.md
│   ├── index.json
│   ├── qwen2.5-coder.md
│   └── gemma4.md
├── strategies/                 # type: Strategy — high-level approaches
│   ├── index.md
│   ├── index.json
│   ├── single-task-focus.md
│   └── fresh-context-per-turn.md
└── references/
    ├── skills/run-java.md      # Executor skill
    └── attesters/output_match.md  # Attester skill
```

### How It Works

1. **Auto-generated** — `okf_generator.py` reads `spec.yaml`, `tasks.json`, `progress_tracker.json`, and `CHANGELOG.md` to produce the bundle after every state change.

2. **Skill learning** — `skill_recorder.py` lets you record new skills, failure modes, and model profiles as OKF concepts. The agent can search these by tags or type before each turn.

3. **Pre-turn context injection** — `ralph.sh` searches relevant skills and failure modes, then injects a summary into the prompt context so the agent can reference known techniques.

4. **Failure observation** — When verification fails, `task_runner.py` automatically records the failure pattern with the model's reasoning for future reference.

### Usage

```bash
# Seed the bundle from existing codebase (run once)
SANDBOX_DIR=sandbox python3 skill_recorder.py seed

# Record a new skill
SANDBOX_DIR=sandbox python3 skill_recorder.py record skills "skill-id" "Skill Title" "tag1,tag2" "## How to Use\n\n..."

# Record a failure mode
SANDBOX_DIR=sandbox python3 skill_recorder.py record failure-modes "failure-id" "Failure Title" "tag1,tag2" "## Symptom\n\n..."

# Record a model profile
SANDBOX_DIR=sandbox python3 skill_recorder.py record model-profiles "model-name" "Model Profile" "model,tag" "## Model: ...\n\n..."

# Search skills by tags
SANDBOX_DIR=sandbox python3 skill_recorder.py search --tags "parser,java"

# Search by type
SANDBOX_DIR=sandbox python3 skill_recorder.py search --type "Failure Mode"

# List all skills
SANDBOX_DIR=sandbox python3 skill_recorder.py list

# Regenerate the full OKF bundle
python3 okf_generator.py sandbox
```

### OKF Concept Types

| Type | Purpose | Example |
|------|---------|---------|
| `Project` | The spec.yaml as a knowledge concept | Project metadata, validation table |
| `Attested Computation` | One verification task | "N=11 produces 563d8e..." |
| `Model` | Per-model evaluation results | "qwen2.5-coder:7b — 2/7 tasks passing" |
| `Skill` | Learned technique or pattern | "Think-tag stripping" |
| `Failure Mode` | Known failure pattern + fix | "Compile-before-write loop" |
| `Model Profile` | Model-specific characteristics | "qwen needs think-tag cleanup" |
| `Strategy` | High-level approach | "Single-task focus per turn" |

### Trust Tiers

OKF concepts carry trust signals derived from verification state:

- **unverified** — Task is `failing`, no verification record
- **machine-confirmed** — Task is `passing`, verified by `process:regression-gate`
- **human-reviewed** — Verified by a `human:` actor (ready for manual sign-off)

### Lifecycle

| State | Meaning |
|-------|---------|
| `draft` | Task is failing, not yet verified |
| `stable` | Task is passing, verified |
| `deprecated` | Kept for history, no longer current |
